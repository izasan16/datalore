# Datalore 前端 UI/UX 布局整改设计

## 1. 背景与目标

当前前端功能已经覆盖工作台、数据源、数据管理、SQL 分析、API 发布和授权应用，但多个页面使用了与内容无关的满高 Card，造成大面积空白、信息层级弱和操作入口不够明确。本次整改聚焦现有功能的视觉组织，不新增业务能力、不改变后端接口契约。

目标：

- 让页面高度由内容和任务决定，避免少量内容被大卡片撑满。
- 让每个页面的主任务、状态和下一步操作一眼可见。
- 保留并强化现有 API 授权应用能力。
- 统一加载、空态、错误态、操作反馈和响应式行为。
- 在不影响现有业务流程的前提下减少重复入口和装饰性元素。

## 2. 范围与非目标

范围包括 `web/src/pages` 下的工作台、数据源、数据管理、SQL Lab、API 发布、授权应用页面，以及工作区应用壳和全局样式。

本次不包含：新增工作流或设置业务功能、修改数据库模型、修改 API 鉴权规则、重新设计登录注册业务流程、引入新的 UI 框架。

## 3. 统一布局原则

### 3.1 页面骨架

应用壳保留左侧导航、顶部用户区和内容区。内容区页面统一使用：

1. 页面标题区：标题、简短说明、主操作。
2. 主内容区：按任务组织的表格、表单或编辑区域。
3. 辅助状态区：仅在有内容时展示最近使用、提示或上下文信息。

页面内容少时使用自然高度，不使用无条件 `height: 100%` 撑满 Card。只有 SQL 编辑器等确实需要占据剩余空间的交互区域使用 flex 填充。

### 3.2 卡片与间距

- 普通业务 Card 采用内容自适应高度。
- 只有页面级编辑器、结果面板等明确需要滚动的区域使用 `card-fill` 和内部滚动。
- 同一页面的区块间距保持 16px；页面边距保持现有 20px 基准。
- 卡片只用于划分任务区域，不用来包裹每一个字段或制造视觉层级。

### 3.3 操作层级

- 每页最多一个主要 CTA，放在标题区或表单底部。
- 取消、返回等重复动作只保留一个明确入口。
- 图标按钮提供 `title` 或可访问名称。
- 可点击列表项使用真实链接语义或按钮语义，不使用仅绑定点击事件的伪链接。

### 3.4 状态规范

- 加载中：显示局部 Skeleton 或明确的加载状态，不直接返回空白。
- 空数据：说明当前没有数据，并提供与当前页面任务对应的主操作。
- 加载失败：显示错误原因和重试入口；不得静默吞掉关键请求错误。
- 保存/发布：成功后给出明确反馈并引导到下一步；失败保留用户输入。

## 4. 页面设计

### 4.1 工作台

采用已确认的 B 方案：紧凑快捷入口 + 工作区信息。

- 三个快捷入口卡片按内容定高，约 140–180px，不再撑满剩余视口。
- 卡片只呈现模块名称、用途说明和一个主要动作。
- 下方增加最近使用、数据源状态或工作区信息区域；没有数据时使用紧凑空态。
- 不展示对用户任务无帮助的内部字段，例如 `tenantId`。
- Header 左侧不保留无意义空白，可用于页面上下文或保持简洁。

### 4.2 数据源

列表页使用紧凑表格或列表呈现名称、类型、连接状态和最近更新时间，主操作为新建数据源。创建页按“连接信息 → 测试连接 → 保存”组织，测试结果就近展示。列表为空时使用短空态，不让空 Card 撑满页面。

### 4.3 数据管理

列表页突出数据集名称、来源、更新时间和主要操作；空态直接提供新建数据集入口。新建页将数据集基本信息、字段/权限配置和保存动作分组，避免把单个字段单独占据整行造成空白。

### 4.4 SQL Lab

编辑器和结果区继续保留可用的纵向工作流：上方脚本/编辑区域，下方结果区域。编辑器和结果区使用 flex 分配剩余空间，只有需要滚动的区域滚动。结果为空时显示紧凑的说明，不使用巨大的空白面板。脚本列表保留选中态和删除操作，但图标操作需要可访问名称。

### 4.5 API 发布列表

标题区提供“新建 API”主操作。列表项突出 API 名称、访问路径、启用状态和更新时间，操作集中在行尾。空态同时说明 API 发布用途并提供新建入口。详情进入使用真实链接语义，避免伪 `<a onClick>`。

### 4.6 API 新建

采用已确认的 A 方案：分组式紧凑表单。

1. 基础信息：API 名称、访问路径。
2. 数据权限：数据集、暴露列、可过滤列。
3. 调用限制：单次最大行数与相关限制字段就近排列。
4. 底部操作：发布 API，以及发布后如何获取 AppKey、配置授权和调用 API 的提示。

删除顶部“返回列表”和底部“取消”的重复表达；字段选择区域限制最大高度并提供全选/清空等效率操作。数据集加载失败必须可见并可重试。

### 4.7 API 详情

采用已确认的 A 方案：顶部概览 + 下方配置区。

- 顶部展示 API 名称、启用状态、访问地址和调用方式。
- 下方按内容顺序组织调用配置、授权应用、调用示例。
- 保留现有授权应用勾选和保存关系的功能，但不使用左右双栏强制等高布局。
- 没有授权应用时显示创建应用/进入应用管理的明确入口。
- 调用示例就近展示路径、请求方式、鉴权信息和示例代码。

### 4.8 授权应用管理

保留现有 `/apipub/apps` 功能：应用创建、列表、改名、删除、AppKey/AppSecret 查看与复制。页面标题区说明应用用于调用已授权 API；无应用时提供创建入口。Secret 展示遵循现有安全行为，不在视觉整改中扩大暴露范围。

### 4.9 导航

隐藏当前未开发的“工作流”和“设置”菜单项，同时移除“灰色菜单为后续迭代模块”的重复说明。数据管理与 API 发布使用语义更清晰的图标，提升模块识别度。

## 5. 响应式与可访问性

- 桌面端保持现有侧栏和内容密度。
- 窄屏下双栏自动转为单栏，操作按钮允许换行但不被压缩到不可用。
- 表格或长字段提供横向滚动，不强行缩小核心文本。
- 所有图标按钮提供 `title`/`aria-label`；焦点态保持可见。
- 颜色仅作为状态辅助，状态同时使用文字或图标表达。

## 6. 实施顺序与验证

实施顺序：应用壳与全局令牌 → 工作台 → 数据源/数据管理 → SQL Lab → API 列表/新建/详情 → 授权应用管理 → 全局状态和可访问性收口。

每个页面完成后验证：正常数据、空数据、加载中、加载失败、保存失败、窄屏布局和核心导航路径。最终运行现有前端构建与测试命令，并通过浏览器逐页检查无水平溢出、无不必要的满屏空白、主要 CTA 可见且授权应用流程可达。

## 7. 验收标准

- 工作台快捷入口不再撑满整屏，首屏有工作区信息或紧凑空态。
- 业务内容少的页面不再出现无意义的满高 Card。
- API 新建页没有重复的返回/取消入口，字段选择区域可控高。
- API 详情页保留并能操作授权应用功能，且不被大面积空白包围。
- 未开发菜单不再出现在导航中。
- 所有关键请求的加载失败和空态均有可见反馈。
- 桌面和窄屏下主要任务、主要操作和页面层级清晰可用。
