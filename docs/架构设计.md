## 1. 八个开放问题的决策

### Q1 同步引擎选哪家？

**决策：DataX，以子进程方式嵌入。**

- 团队是 Java 栈，DataX 也是 Java；任务模型是 JSON 配置，由后端生成后 `java -jar datax.jar job.json` 调起，无守护进程、无集群要养，Docker Compose 里加一个基础镜像即可。
- 源/目标覆盖与旧系统对齐：MySQL、Oracle、SQLServer、PostgreSQL、Hive 等，正好覆盖「用户插拔数据存储」的参考清单。
- 落选理由：Flink CDC 只解决增量实时场景，引入整套 Flink 运维不成比例；SeaTunnel 的 Zeta 引擎更现代但社区文档和政企场景成熟度不如 DataX，且需要常驻集群。
- 节奏：MVP 不含引擎（文件上传入库用平台代码直写 PG 的 COPY）；DataX 在 ETL/同步迭代接入。增量同步（CDC）明确不做，后置再议。

### Q2 工作流引擎：自研还是复用？

**决策：自研轻量 DAG 状态机 + Quartz 调度。**

- 节点类型收敛为四种：SQL 节点、同步节点（DataX 任务）、Python 节点（阶段 2）、通知节点。
- 实现：DAG 拓扑存库（node/edge 表），实例按拓扑序执行，节点失败可配重试次数，实例状态机 `PENDING → RUNNING → SUCCESS/FAILED/CANCELED`。
- 落选理由：DolphinScheduler/Airflow 都要独立集群和专用 Worker，对 1-2 人团队 + Compose 部署是负资产。
- Python 节点接入时，容器池只是执行器的一种，状态机不变。

### Q3 多租户数据隔离粒度？

**决策：双轨制。**

- **系统元数据**（租户、用户、数据源注册表、脚本、图表、API 定义等）：内置 PG 单库共享 schema，所有表带 `tenant_id`，由 MyBatis-Plus 租户插件在 SQL 层强制注入/过滤，杜绝漏过滤。
- **租户数据区**（用户自己的表、上传入库的数据）：内置 PG 中**每租户一个独立 schema**（`tenant_{id}`），建租户时自动创建。用户在此任意建表。
- SQL Lab 执行 SQL 时走后端 SQL 网关：连接租户数据区连接池、`SET search_path = tenant_{id}`，并施加语句超时、行数上限、危险语句拦截。
- 落选理由：纯 tenant_id 行级隔离扛不住「用户任意建表」的场景；独立 database 每租户开销大且难运维。schema 是 PG 下用户自建表场景的标准解。

### Q4 可视化重做的交互范围？

**决策：图表类型白名单先行，交互深度分期。**

- MVP 图表白名单：柱状、折线、饼图、明细表、指标卡。统一一个「字段拖拽 → 维度/度量映射 → 图配置」的分析模型（对标网易有数的核心交互）。
- 联动、钻取、地图、自定义主题等：MVP 后按用户反馈排期。
- 正式开发前单独做一轮 UI/UX 设计（Arco 体系内出高保真），不边做边定。
- 优先级调整：可视化能力保留，但暂不作为 API 发布后的下一项；先完成数据同步与工作流闭环，再单独排期可视化 MVP。

### Q5 「用户插拔数据存储」的深度？

**决策：分阶段。**

- MVP/第一阶段：外部源**只读**——注册连接、测试连通、浏览表结构、SQL 查询、作为 DataX 同步的源端。
- ETL 迭代：放开作为**同步目标端**（写入用户自己的库）。
- 凭据安全：连接密码 AES-GCM 加密存储，密钥走环境变量；连接池按数据源维度懒加载、空闲回收。

### Q6 门户（potal）怎么退化？

**决策：退化为「租户工作台」。**

- 登录后首页 = 工作台：我的图表/仪表盘列表、常用数据源入口、最近使用的脚本。
- 不做面向组织外部的门户站点搭建（那是交付项目形态，SaaS 不需要）。
- 信息架构设计时出工作台布局稿。

### Q7 Python 容器池资源模型？（阶段 2 决策，先定方向）

**决策：每租户配额 = 并发容器数上限 + 单容器 CPU/内存 limit（Docker API 动态创建/回收）。**

- 配额数据模型参考旧系统 `jupyterusers` 表的 cpu/memory 字段。
- 平台管理员可调租户配额；超限排队。

### Q8 Python SDK 形态？（阶段 2 决策，先定方向）

**决策：自研 `Datalore-sdk` Python 包，通过平台 REST API + 租户 token 读写数据。**

- 不向用户直接发库连接串——所有数据访问过平台权限与审计。
- SDK 提供三类原语：读数据集（DataFrame）、写回数据集、调用已发布 API。
- Notebook 容器内预置 SDK 并注入 token。

## 4. 风险与既知约束

1. **中文路径**：仓库位于 `D:\极智\Datalore`（含中文）。Maven/npm 一般可处理，但个别工具链在 Windows 上对非 ASCII 路径敏感；若构建出现诡异问题，第一排查项是把仓库迁到 ASCII 路径。
2. **PG schema 动态创建**：租户 schema 由后端 DDL 创建，需要应用连接使用可建 schema 的角色；生产部署时用非超级用户 + 预授权数据库。
3. **SQL 网关是安全重心**：任意 SQL 执行 + 多租户场景，语句白名单/超时/行限/连接隔离是硬要求，在子计划 5 里以 TDD 覆盖。
4. **DataX 与 PG 17 兼容**：DataX 部分插件对 PG 新版本有兼容性小坑，接入时以 PG 16 为准。
5. **旧系统只作参考**：业务语义参考旧代码与文档，代码一律不搬运（除个别正则/枚举常量等纯逻辑可摘录）。
