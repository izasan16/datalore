## 1. 一句话定位

把旧的极智 DAAS（北规院内网单租户交付项目，Spring Cloud 微服务 + React 16 老前端，946 个 Java 文件 + 1336 个 JS 文件）重写为一个面向**数据分析师和数据开发工程师的 SaaS 数据平台（daaspro）**：真多租户、内置 PostgreSQL 底座、支持用户插拔自己的数据存储、Docker Compose 部署、由 1-2 人 + AI 助手长期迭代。

## 2. 业务范围（做减法的结果）

### 2.1 保留的模块（功能保留，内部业务逻辑删减）

| 模块 | 对应旧系统 | 保留要求 |
|------|-----------|---------|
| 数据源 + 数据管理 | datasource(107js)、metadata、TableController/DataManagerController | 本地库/外部源管理、表结构预览、字段维护 |
| 数据集成 (ETL) | dataetl(45js)、TaskController/ETLController | 任务配置、调度、实例管理；**引擎换成开源同步引擎** |
| SQL 分析 (SQL Lab) | sqllab(29js)、SqlModelController(2168行)/SqlScriptController | 核心生产力工具，SQL 编辑/执行/结果集/脚本管理 |
| 工作流编排 | workflow(71js)、WorkflowService + x6 | **DAG 编排，用于串联 daaspro 各项功能**（SQL/同步/API 等），引擎选型取决于各功能的实现形态 |
| 数据服务 (API 发布) | dataservice(48js)、DataApiController | 把表发布成 REST API、应用授权 |
| 可视化 | chartedit(183js)+dashboard(73js)+potal(50js) | 图表编辑器 + 仪表盘 + 门户保留；**Word 报告明确不要**；目标对标「网易有数」这类成熟 BI 的体验，旧系统交互全部重做 |
| Python 能力三件套 | 程序建模(advancedmodel 28js)、Notebook(jupyter)、模型超市(modelmarketnew 34js) | 详见 2.2a，**第二阶段（MVP 后第一个迭代）**，但架构需预留位置 |

### 2.2a Python 能力（第二阶段，架构预留）

用户回加的三块，围绕「用户写 Python 跑数据」这一核心诉求，分工按**探索 vs 生产**划分，共享同一个执行底座（容器池）：

| 模块 | 场景定位 | 说明 |
|------|---------|------|
| Notebook (Jupyter) | **探索**：交互式逐格执行、看图、试参数，偏分析师 | 每租户/用户独立 Jupyter 容器（对接 JupyterHub 思路），旧系统即此模式 |
| 程序建模 | **生产**：脚本注册成可复用「模型」，偏数据开发 | 摒弃旧系统的 Runtime.exec + 硬编码路径方式，走容器池任务队列 |
| 模型超市 | 模型的共享/复用界面：**把脚本抽出参数，方便复用和定时运行** | 做成「共享脚本库」形态（公共/我的/定时三视图 + 参数化运行 + 运行历史），不单独做市场页、不做跨租户交易 |

**Python 能力边界（四项全要）：**
1. 平台提供 Python SDK，脚本内直接读写内置 PG 和用户挂载的外部数据源；
2. 运行结果可回写平台成为数据集/表，供后续 SQL/API/可视化使用；
3. Python 脚本可作为工作流的一个节点类型被 DAG 调度；
4. 训练好/成熟的脚本可一键发布成 REST API 服务（对应旧系统 PythonOnlineDepolyTask + localapi5 的模型服务化能力，实现方式重做）。

### 2.2 砍掉的模块

- AI 应用、智能问数、SQL 助手（后续有需求单独立项）
- Word 报告
- 沙箱（独立沙箱环境不需要；Python 执行环境由 Notebook/程序建模的容器底座承担）
- 数据填报（dataentry 47js + 填报审核流 + 4 个 Datainput 定时任务）——注意：这与 docs 需求文档的「足迹范围」不同，**用户明确说 docs 需求文档没有意义，本次范围以本文件为准**
- 数据质量、离线同步（周边可后置再议）
- 旧的权限大而全体系（PermController 5051 行）

### 2.3 横切关注点

- **用户与权限**：自带简化版（账号表 + 组织 + 角色），权限模型只按 SaaS 必要项设计（管理员/成员 + 资源所有权），不再做旧系统那种按钮级权限矩阵。
- **多租户**：真多租户，一套实例多客户共用，需要租户模型贯穿数据层。
- **数据底座**：平台内置一个 PostgreSQL（系统库 + 用户默认数据区）；用户可插拔挂载自己的数据存储（外部 JDBC 源，旧系统支持 MySQL/Oracle/SQLServer/Hive/Doris 可作参考清单）。
- **旧数据**：不需要迁移历史用户数据，纯新项目。

## 3. 技术栈共识

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | **Arco Design** + React 18 + Vite + TypeScript | 用户指定 Arco；图表库建议 ECharts（旧系统即 echarts 系），DAG 画布候选 X6（旧系统已用） |
| 后端 | Spring Boot **单体**（React + SpringBoot 单体共识） | 去掉 eureka/zuul/config/feign/rabbitmq 全套微服务设施 |
| 存储 | 平台内置 PostgreSQL | 系统 metadata 库与租户数据区分离由设计阶段细化 |
| 同步引擎 | **开源引擎**（DataX/SeaTunnel/Flink CDC 候选，设计阶段比选） | 替换旧系统内嵌 Kettle 写死在 ETLServiceImpl(814行) 的技术债 |
| Python 执行 | 容器池任务底座（共享）：Jupyter 容器（探索）+ 队列式跑批（生产） | 第二阶段落地；MVP 只需预留脚本任务表和容器池接口位置，不实现 |
| 部署 | Docker Compose | 前端 Nginx + 单体后端 + PostgreSQL + Redis + 同步引擎容器（第二阶段加 JupyterHub/容器池） |
| 团队 | 1-2 人 + AI 助手 | 架构复杂度上限以此为准，任何「为将来准备」的设计都要克制 |

## 4. 上线与验收

- **MVP 先行迭代**：验收不追求对齐旧系统全功能。
- MVP 建议链路：登录/建租户 → 挂数据源/文件上传入库 → SQL 分析跑通 → 发布 API → 简单图表看数。工作流与仪表盘编排随后迭代。
- **第二阶段（MVP 后第一个迭代）**：Python 三件套——Notebook（探索）、程序建模（生产）、模型超市（脚本参数化共享/定时运行），加 SDK 读写/结果回写/工作流节点/API 发布四项能力闭环。
- 每轮迭代的产出必须可部署（Compose 一键起）、可演示。

## 5. 遗留的开放问题（进入设计阶段要回答）

1. 同步引擎具体选哪家（DataX vs SeaTunnel vs Flink CDC vs 自研轻量兜底），取决于支持的源/目标清单和团队运维能力。
2. 工作流引擎：自研轻量 DAG 状态机 vs 复用调度引擎，取决于节点类型收敛到几种。
3. 多租户数据隔离粒度（共享 schema + tenant_id vs 独立 schema/database），影响所有表设计。
4. 可视化重做的交互范围：对标网易有数的哪些具体能力（拖拽分析、联动钻取、主题皮肤…），建议单独做一轮 UI/UX 设计。
5. 「用户插拔自己的数据存储」的深度：只读接入即可，还是要支持写入目标端？
6. 门户（potal）在新 SaaS 形态下是否退化为「租户工作台」，需在信息架构设计时确认。
7. Python 容器池的资源模型：每租户配额（CPU/内存/并发容器数）如何限制与计量（旧系统 jupyterusers 表有 cpu/memory 字段可参考）。
8. Python SDK 的形态：自研 Python 包（平台 API 换 token 读写） vs 直接暴露库连接串（简单但绕过权限）——涉及安全边界，设计阶段必须定。

## 附：旧系统关键事实（侦察所得）

- 后端：Spring Cloud（eureka/zuul/config + feign + rabbitmq + shiro + quartz + mybatis），Java 包名 com.zhzj，业务服务 3 个：ssbi_qsql(729 Java 文件)、ssbi_qsql_manage(141)、ssbi_offline_sync(58)，基础设施 3 个（zuul/eureka/config）。
- JDBC 驱动注册痕迹：PostgreSQL、Hive、Oracle、MySQL、SQLServer。
- 本地库查询前端直查（数据一次加载），集群库（Hive）走后端接口滚动加载。
- 前端：React 16 + Redux + react-router(HashRouter) + antd 3 + less + babel-polyfill + pubsub-js；图表 echarts 系自封装组件（echartsComponent 20+ 图表组件）+ leaflet 地图（mapVComponent）；DAG 用 @antv/x6；无 package.json（构建链缺失）。
- 前端 30 个模块共 1336 个 js；最大模块 chartedit 183、common 151、datasource 107、user 85、dashboard 73、workflow 71。
- 北规院菜单分组：规划应用 / 数据中台（数据管理、数据集成、数据质量、数据发布、离线同步）/ 分析建模（模型超市、SQL分析、程序建模、沙箱、Notebook、AI应用、工作流）/ 制图发布（表盘配置、报表展示、数据门户、Word报告）。
- 旧系统带大量多客户痕迹（BGY/BI/GZW/HUNAN/XJIANG 多套菜单常量、atoken/code/免密登录多套第三方登录逻辑）——新系统统一做成标准登录 + 租户体系，砍掉所有私有登录通道。
